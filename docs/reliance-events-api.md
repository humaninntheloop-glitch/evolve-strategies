# Apply Guide — Machine API for AI Reliance Events

Adds API-key authentication and a `POST /api/v1/reliance-events` endpoint so the
Chrome extension can file AI reliance events as DRAFT permission-slip records.

## Apply order

1. **`prisma/schema.prisma`** (modified)
   Adds the `ApiKey` model plus `apiKeys` on `Organization` and `createdApiKeys`
   on `User`. Copy over the repo's `prisma/schema.prisma`.

2. **`prisma/migrations/20261006183000_add_api_keys/migration.sql`** (new)
   Copy into `prisma/migrations/20261006183000_add_api_keys/migration.sql`.
   UUIDs are generated by Prisma, matching the existing migrations; no new
   database extension is required.

3. Run migrations and regenerate the client:
   ```bash
   npx prisma migrate deploy
   npx prisma generate
   ```
   Apply the checked-in migration in the target environment before enabling the API.
   Do not run `migrate dev` against production.

4. **`src/app/api/v1/reliance-events/route.ts`** (new)
   The machine endpoint. `src/middleware.ts` bypasses browser-session
   authentication for this exact path; the handler requires an API key.

5. **`src/lib/actions/api-key-actions.ts`** (new)
   Server actions for key management (ADMIN only).

6. **`src/app/(dashboard)/admin/api-keys/page.tsx`** (new)
   Admin UI: create / list / revoke keys.

7. **`src/components/layout/nav-links.tsx`** (modified)
   Adds the "API Keys" link under the Admin section (ADMIN role only).

8. **`src/app/(dashboard)/admin/page.tsx`** (modified)
   Adds an "API Keys" card to the admin overview.

9. Verify: `npm run build` (runs `prisma generate && next build`) and
   `npx tsc --noEmit`.

## API contract

```
POST /api/v1/reliance-events
Authorization: Bearer hitl_<64 hex chars>
Content-Type: application/json
```

Body (JSON):

| Field | Type | Required | Notes |
|---|---|---|---|
| `aiToolUsed` | string[] | yes | min 1; e.g. `["CHATGPT"]`; `"OTHER"` needs `aiToolUsedOther` |
| `aiToolUsedOther` | string | no | max 200 |
| `aiOutputImpact` | enum | yes | one of `INTERNAL_NOTES`, `INTERNAL_RESEARCH`, `INTERNAL_DOCUMENT`, `CLIENT_COMMUNICATION`, `EXTERNAL_REPORTS`, `FINANCIAL_LEGAL`, `REGULATORY_COMPLIANCE` |
| `dataSensitivity` | boolean | yes | JSON-native boolean (unlike the form action's `"true"`/`"false"` strings) |
| `aiUsageType` | string[] | yes | min 1 |
| `aiUsageTypeOther` | string | no | max 500 |
| `humanReviewPlan` | string[] | yes | min 1 |
| `humanReviewPlanOther` | string | no | max 500 |
| `aiUseJustification` | string[] | yes | min 1 |
| `aiUseJustificationOther` | string | no | max 500 |
| `intendedUseDescription` | string | no | max 2000 → `Record.intendedUseDescription` |
| `aiSummary` | string | no | max 20000 → `Record.aiSummary` |
| `sourceUrl` | string (url) | no | max 2000 → audit log metadata |
| `capturedAt` | string (ISO datetime) | no | → audit log metadata |

Responses:
- `201` — `{ "id": "<uuid>", "status": "DRAFT", "url": "/permission-slips/<uuid>" }`
- `401` — missing/malformed/inactive key
- `400` — invalid JSON
- `422` — `{ "error": "Validation failed", "issues": [{ "path", "message" }] }`
- `429` — over 100 req/min per key (in-memory bucket; see TODO in route for Redis)

Behavior notes:
- Creates the `Record` with `status: "DRAFT"`, `organizationId` from the key,
  `creatorId` = the key's creator (an ADMIN). `distributionContext` /
  `highStakesDecision` are derived with the same helpers as `createRecord`
  (copied into the route — the `"use server"` actions module cannot be imported
  from a route handler).
- Writes an audit log: action `RECORD_CREATED_VIA_EXTENSION`, actor = key creator,
  `newState: "DRAFT"`, metadata `{ sourceUrl, capturedAt }`.
- The reviewer workflow is unchanged: the draft appears in the normal queue and
  goes through the existing submit → approve/reject → record lifecycle.
- No request bodies are logged (payloads may contain PII).

## Key format

`hitl_` + 64 lowercase hex chars (32 random bytes). Only the SHA-256 hex digest
is stored (`key_hash`, unique); `key_prefix` holds the first 12 chars for display.
Plaintext is returned exactly once at creation.

## Notes for the Chrome extension workstream

- The extension must send `Authorization: Bearer <key>` and declare
  `https://humaninntheloop.com/*` (or the deployment host) in `host_permissions`
  so its `fetch` calls are not CORS-blocked.
- The returned `url` is a relative deep link — the extension should prefix it
  with the configured platform origin.
- Keys are issued per organization by an ADMIN at `/admin/api-keys`; one key per
  deployment/customer is the recommended granularity. Revoking a key
  immediately 401s all its traffic.

## Review adjustments and deployment gates

- Strict bearer-token parsing; inactive/non-admin creators or creators moved to
  another organization cannot use previously issued keys.
- Record, audit log, and successful-use timestamp are committed in one transaction.
- Error logs omit exception objects as well as request bodies.
- Rate-limit buckets are allocated only for valid keys and expired buckets are
  cleaned up. The limiter remains local to each instance, not a global quota;
  replace it with shared storage before relying on it for production enforcement.
- No live database migration was run as part of applying this package.
- Run authenticated integration checks with an isolated database: create/list/
  revoke keys, missing/invalid/revoked key 401, malformed JSON 400, invalid payload
  422, valid draft 201, cross-organization isolation, audit rollback, and rate
  limit 429. Retries are not idempotent and can create duplicate drafts.
